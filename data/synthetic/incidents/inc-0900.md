# INC-0900: Intermittent DNS failures after CoreDNS chart upgrade

## Summary
For ~50 minutes, roughly 8% of in-cluster DNS lookups timed out. Cause: the CoreDNS add-on
upgrade (1.10 → 1.11.1) reset the deployment's anti-affinity, and all three CoreDNS replicas
landed on one `system` node that was under memory pressure.

## Impact
`ledger-service` and `checkout-web` saw sporadic 5 s latency spikes (one DNS timeout each).
No SLO breach; error budget burn 0.4%.

## Symptoms
- `EAI_AGAIN` in `checkout-web` logs
- `coredns_dns_request_duration_seconds` p99 jumped from 2 ms to 5 s
- `kubectl get pods -n kube-system -l k8s-app=kube-dns -o wide` → all replicas on `ip-10-40-17-44`

## Timeline (UTC)
- 08:55 EKS add-on `coredns` updated via Terraform (staging soak had passed).
- 09:12 Alarm `eks-prod-coredns-errors`. Page `pe-oncall`.
- 09:30 Noticed co-location; the node had 92% memory use from Prometheus.
- 09:41 `kubectl rollout restart deploy coredns -n kube-system` — pods rescheduled across nodes; errors stop.
- 10:05 Resolved after 20 min clean.

## Investigation
The add-on's default configuration overwrote the `podAntiAffinity` Acme had set with
`configuration_values`. `--resolve-conflicts OVERWRITE` had been used.

## Root cause
Add-on upgrade with `OVERWRITE` discarded custom scheduling configuration.

## Remediation
Re-applied `configuration_values` with `topologySpreadConstraints` (zone + hostname) and
`--resolve-conflicts PRESERVE`.

## Prevention
- `PRESERVE` is now the default in `modules/acme-eks/addons.tf`.
- Alert if CoreDNS replicas share a node (`count by (node) (kube_pod_info{pod=~"coredns.*"}) > 1`).
